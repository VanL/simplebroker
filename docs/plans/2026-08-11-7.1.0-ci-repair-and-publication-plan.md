# 7.1.0 CI Repair and Coordinated Publication Plan

Date: 2026-08-11
Status: active
Class: 4 — test-harness repairs feed coordinated, immutable publication of
three packages.
Plan type: CI repair and release execution; no product-contract change.
Hardening: required for exact-SHA release gates, immutable tags, and
irreversible PyPI publication.

## Goal

Repair every deterministic or intermittent test defect exposed by the 7.1.0
release candidate, prove each correction at its owning state boundary, then
run `bin/release.py all` from clean `main`. The driver must push the repair,
wait for exact-SHA `Test`, `Test Postgres Extension`, and `Test Redis
Extension` workflows, and only then create the coordinated tags:

- `v7.1.0`
- `simplebroker_pg/v3.6.0`
- `simplebroker_redis/v3.6.0`

Flakiness is a defect. Reruns and larger timeouts are not dispositions.

## Invariants and Boundaries

1. Product watcher, runner, phase-lock, queue, storage, and public API behavior
   do not change.
2. Each test asserts state it owns. Wall time remains only a deadlock safety
   valve; no timeout is raised to hide scheduler dependence.
3. The watcher oracle reads a stable, locked instrumentation snapshot and uses
   the latest observation, not any historical positive value.
4. The runner proof retains a real setup lock, a real runner contender, a
   marker written while the lock is held, proof that the contender has not
   completed before release, and exact post-release result/operation checks.
5. No required exact-SHA workflow failure may be waived or retried as the
   release disposition. Diagnose, repair, commit, and run a new SHA.
6. No tag is created until all three required workflows are green for the same
   SHA and that SHA remains reachable from `origin/main`.
7. Release tags are write-once. PyPI publication is irreversible. A later
   product defect requires a new version, never a moved tag.
8. The release driver may create a release metadata commit only if its owned
   files change. Unrelated files must not be staged.

## Implementation and Verification

1. Retrieve failing job logs with authenticated `gh` commands and preserve
   job/run identifiers in the evidence log.
2. For each failure, construct the narrowest red-capable proof available,
   minimize the state predicate, apply the test-only correction, and stress
   the live integration. Do not modify product code.
3. Run focused tests, neighboring modules, Ruff, format, MyPy, document gates,
   and an independent scoped review with round-two verification for accepted
   findings.
4. Commit the repair with its root cause in the commit message. Confirm a
   clean `main` and absent release tags.
5. Run `bin/release.py all` without `--skip-checks`. Let it run all local
   core, benchmark, PostgreSQL, Redis, examples, static, lock, build, and
   packaging gates; push `main`; and wait for exact-SHA CI.
6. If any exact-SHA job fails, stop before tags, add its root cause to the
   disposition table, and repeat from step 1 with a new repair SHA.
7. After the driver pushes tags, monitor all three release-gate workflows to
   terminal success. Verify PyPI and GitHub Releases for all versions, then
   install the exact published trio in a clean Python 3.11 environment and
   resolve both first-party plugins.

## Anti-Mocking and Acceptance

- Do not mock `PollingStrategy`, the real watcher thread, the phase lock, or
  `SQLiteRunner.run_exclusive_setup` in their live proofs.
- Pure predicate tests may use explicit delay traces because the trace
  classifier is the unit under test.
- Test-owned setup-marker publication must use the runner's real
  `PhaseLockService.mark_phase()` path while the coordinating thread owns the
  lock. Direct status-sidecar publication is valid only when `mark_phase()`
  returns `False`, which is the service's platform fallback.
- Acceptance requires targeted red/green evidence, repeated live tests, full
  local release gates, exact-SHA cross-platform CI, tag-triggered release
  gates, published artifacts, and clean-install resolution.

## Stop Gates, Rollback, and Success Signals

- Stop and revise if a repair needs product code, a dependency, a public
  contract change, or a second execution path.
- Stop before tags on any required CI failure, dirty worktree, version/floor
  mismatch, repository-setting failure, or loss of `origin/main` ancestry.
- Before tags, rollback is an ordinary revert of repair commits. After tags or
  publication, never move or delete release identifiers; use a corrective
  version if needed.
- Success signals: all required workflows green on one SHA; all tag release
  gates green; PyPI and GitHub report core 7.1.0 plus both extensions 3.6.0;
  a clean install imports and resolves PostgreSQL and Redis plugins.
